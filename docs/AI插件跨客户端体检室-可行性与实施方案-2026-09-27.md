# AI 插件跨客户端体检室：可行性核查与实施方案

> 研究日期：2026-09-27。定位为**本机已安装客户端中的插件发布验收包**。本文件是立项方案与验证门槛，尚未声称完成真实模型运行或用户需求验证。

## 1. 立项结论

**有条件可做，但必须缩小原始设想。** 首版只验证本机 Codex CLI 与 Claude Code 中的 MCP 工具型插件，以“同一发行包在具体客户端版本上是否装得上、看得见、会被正确调用、能完成指定任务”为核心问题。产物是一份可追溯的本地证据包，而非又一个通用 MCP 调试器。

原设想中的“跨模型任务评测”已被 [MCPJam Evaluate](https://docs.mcpjam.com/inspector/evals) 覆盖，包括真实 Codex／Claude Code harness、工具调用断言、负例、重复运行和回归门禁。[mcp-interop](https://github.com/git-ksk/mcp-interop) 已覆盖真实客户端的连接、认证、初始化和工具发现，并明确不宣称工具正确性或模型选用。[官方 conformance 套件](https://github.com/modelcontextprotocol/conformance) 覆盖协议符合性。因此本项目的价值假设只能是：**插件作者希望在自己和用户实际安装的客户端、版本与配置上，用本地方式完成安装态到任务态的发行验收，并获得指向故障层的证据和修复建议。** 这是假设，需通过第 4 节验证。

## 2. 已完成的可行性核查

| 核查项 | 当前证据 | 判断 |
|---|---|---|
| 本机执行环境 | Windows；Node `24.14.1`、Java 21；Codex CLI `0.158.0-alpha.2.1`、Claude Code `2.1.89`、VS Code `1.120.0` 已安装；Cursor CLI 和 Go 未找到 | 具备两个 CLI 客户端的原型入口；不能承诺 Cursor／macOS 覆盖 |
| Codex 非交互运行 | 本机 `codex exec --help` 显示 `--json` JSONL、`--ephemeral`、`--ignore-user-config`、`--sandbox read-only`、`--cd`；OpenAI 的[技能评测实践](https://developers.openai.com/zh-Hans/blog/eval-skills)也展示按真实事件做确定性检查 | 可构造 runner；**当前执行环境的 `codex login status` 因无法解析 home 目录而失败**，认证与模型调用仍须在原型中实测 |
| Claude 非交互运行 | 本机 `claude --help` 显示 `-p`、`--output-format stream-json`、`--mcp-config`、`--strict-mcp-config`、`--max-budget-usd`；[官方文档](https://code.claude.com/docs/en/headless)解释结构化事件与 `--bare` 隔离 | 有 runner 入口；当前安装版本 **2.1.89 早于官方文档中若干新事件字段的最低版本**，只能按实测字段解析，不能照搬最新文档的事件契约 |
| MCP 样例服务 | [官方 TypeScript SDK](https://ts.sdk.modelcontextprotocol.io/v2/)提供 stdio 与 Streamable HTTP；v2 [协议版本指南](https://ts.sdk.modelcontextprotocol.io/v2/protocol-versions)区分 2025 和 2026 两代握手 | 首轮固定 stdio 与客户端实际协商版本；HTTP／OAuth 放在后续门槛 |
| 本地资产复用 | 工作区 `mcp-sentinel` 已做工具定义 lockfile、静态风险与 SARIF；其 README 明确不执行 `tools/call` | 可把它当静态证据来源；不复制其静态扫描逻辑，也不把其结果写成运行时通过 |
| 其他客户端 | VS Code 已装并有[官方 MCP 配置说明](https://code.visualstudio.com/docs/agent-customization/mcp-servers)；ChatGPT 官方[插件测试流程](https://developers.openai.com/plugins/deploy/connect-chatgpt)要求接入、测试完整插件 | 首版仅给这两者手工验收模板；不宣称后台自动化。Cursor 本机缺失，标记未测试 |

**核查的边界：** 上述是文档、CLI 入口和本机环境检查，并没有消耗模型调用、安装样例插件、获取真实 `tools/call` 轨迹或完成端到端验收。因此“可做原型”有证据，“已证明产品端到端可行”尚无证据。

## 3. 产品定义与可交付边界

### 目标用户和实际动作

首要用户是同时使用多个 AI 客户端、自己编写或维护 Skills／MCP 插件的重度用户和开发者。给定一个本地插件目录或 MCP 服务配置、目标客户端、任务用例，工具在隔离的临时工作区启动实际客户端，输出一份发行报告。报告包含客户端和插件版本、环境条件、每个任务的实际调用与结果、未覆盖的能力、可复现命令和敏感信息脱敏后的证据。

### 证据分层（每层独立状态）

| 层级 | 验证的问题 | 首版方式 | 允许写“通过”的证据 |
|---|---|---|---|
| E0 静态 | 包结构、配置、工具定义是否合理 | 读取 manifest／配置；可调用 `mcp-sentinel` | 解析或静态扫描结果；只表示静态通过 |
| E1 协议 | 服务能否握手、列工具、调用受控工具 | SDK 直连；可接官方 conformance | 原始请求、响应与协商版本 |
| E2 客户端发现 | 具体版本的真实客户端能否加载该服务 | 临时配置运行 Codex／Claude | 客户端事件加服务端会话日志相互印证 |
| E3 任务行为 | 给定任务是否选对工具、参数正确、输出基于返回数据 | 实际客户端模型回合；受控 fixture | 服务端 `tools/call`、客户端轨迹、确定性断言三者一致 |
| E4 完整插件体验 | Skill 激活、UI、权限提示与 ChatGPT／VS Code 体验 | 首版人工签署的检查表 | 明确写“人工验证”，附版本、步骤与截图；没有证据则为未测试 |

状态必须是 `PASS / FAIL / UNKNOWN / SKIP`，并保留失败重试。E0/E1 通过不能推断 E2/E3 通过；模型最终回答看起来正确，也不能替代工具调用证据。

### 首版明确范围

- **包含：** Windows 本机、Codex CLI 与 Claude Code、stdio MCP 工具、单插件／单服务器、单轮直接任务和反例、JSON + HTML 本地报告、CLI 运行、基线比较。
- **延后：** Streamable HTTP、OAuth、MCP Apps UI、Skills 激活自动验收、ChatGPT／VS Code／Cursor 自动控制、多租户云服务、广义安全审计。
- **禁止夸大：** 不以模拟 host 的结果标注真实客户端通过；不以“工具已发现”标注任务成功；不因某次重试成功覆盖前面的失败。

## 4. 先做的两项立项门槛（优先于平台开发）

### 门槛 A：竞品差异是否真实存在，预计 1–2 天

拿同一份 fixture 和用例在 MCPJam 的真实 harness 里跑一次，并填写对照表：安装本机插件包、使用用户本机精确版本、读取原有配置与权限、记录服务端调用、生成可离线分享的发行证据、给出可执行修复建议。只记录实测，不根据营销页推断不支持。再请至少 **3 位插件作者／重度用户**评价报告是否解决过他们实际遇到的跨客户端故障；至少 2 位能提供具体故障或愿意拿自己的插件试用，才继续。若 MCPJam 已能同等完成这些动作且试用者无新增需求，停止独立产品开发，转为 MCPJam 用例模板或既有工具集成。

### 门槛 B：真实客户端双端闭环，预计 2–4 天

建立只返回虚构数据的 stdio fixture：`lookup_release` 返回带随机 `run_id` 的发布记录，`delete_release` 是记录到临时文件的**无破坏**模拟动作。对 Codex 与 Claude 各跑 4 类任务：直接查询、间接意图、无关问题不调用、需要危险动作时不应未经明确指令调用。每条至少 3 次；这是工程稳定性试验，不是总体成功率统计。固定任务文本、客户端与模型版本、fixture 哈希，记录每次完整退出码、启动日志、客户端 JSONL、服务端调用日志和最终输出。

**通过条件：** 两个客户端都能在隔离目录装载 fixture；每个至少一次真实 `tools/call` 可由双侧记录关联；正例调用名与参数可确定性断言；负例无调用；无认证、超时或权限问题被错误写为 PASS。若某客户端无法稳定采证，先降级为仅 E0–E2，暂停 E3 和“跨客户端任务验收”的产品承诺。Codex 当前 home 解析异常是首个待排查阻碍；Claude 2.1.89 的事件字段以实际输出为准。

**隔离方式：** 新建临时工作区与最小配置，使用只读沙箱／受限工具权限；Claude 优先用 `--bare --mcp-config --strict-mcp-config`，Codex 用 `--ephemeral --ignore-user-config --sandbox read-only` 并注入一次性 MCP 配置。[Claude 官方文档](https://code.claude.com/docs/en/headless)指出 `--bare` 不读取订阅登录或系统钥匙串，需要 `ANTHROPIC_API_KEY` 或 `apiKeyHelper`；因此 API 凭据是否可用是门槛的一部分，不能假定本机登录即可运行。Codex 的认证同样需要在 home 解析问题修复后确认。不得复制密钥到报告。仅运行自己编写、无外部副作用的 fixture。记录模型费用并设置单次预算和超时。任何客户端无法在不加载用户全局插件／钩子的情况下运行，则不进入自动化 MVP。

## 5. 通过门槛后的 MVP 设计

### 使用流程

1. `doctor init` 读取插件目录或 MCP 配置，生成可编辑 `doctor.yaml`：目标客户端、任务、期望工具、参数断言、禁止调用、超时和证据级别。
2. `doctor preflight` 检查运行时、版本、包路径、所需凭据是否可用；只输出凭据存在性，不打印值；可选调用 `mcp-sentinel` 和官方 conformance。
3. `doctor run` 为每个客户端生成独立的临时工作区与配置，启动实际客户端，收集 JSONL 和服务端事件；失败立即归因到安装、握手、发现、权限、模型选用、参数、工具结果、最终回答。
4. `doctor report` 生成本地 HTML／JSON 证据包和版本矩阵。每个结论可展开原始证据；未知或跳过不会显示绿色。
5. `doctor compare` 把更新前后同一用例、同一目标版本的结果对比；模型版本不同则明确标记不可严格归因。

### 技术结构

Node.js + TypeScript CLI；官方 MCP TypeScript SDK 构造 fixture／直连探针；分别实现 `CodexAdapter`、`ClaudeAdapter`，仅负责启动、事件解析和配置注入；公共事件模型统一为 `client_init / server_discovered / tool_selected / tool_called / tool_result / final_answer / error`。把客户端日志与 fixture 服务端日志按每次唯一 `run_id` 关联。报告引擎只接受带来源、时间、客户端版本和原始记录引用的断言。`mcp-sentinel` 通过独立 CLI 接入，减少与现有 Java 项目的耦合。

**最小数据契约：** `run_id`、插件哈希、客户端可执行文件路径及版本、模型标识、MCP 协商版本、场景 ID、开始结束时间、每次实际工具名和参数、断言状态、证据文件哈希、错误码、覆盖等级。默认剔除密钥、Authorization 头、用户主目录绝对路径；保留可手动复现的脱敏命令。

### 首版验收清单

- 两个客户端、一个受控 fixture、一个真实开源或自研 MCP 服务，各有至少 4 个任务用例。
- 正例、负例、工具返回错误、服务启动失败都被正确分类；失败不会变成空白或“通过”。
- 从 HTML 报告可定位到每项结论的客户端事件与服务端事件；相同输入可重跑。
- 模拟一次工具描述或 schema 变更，能发现前后任务行为差异，并保留两个客户端的原始结果。
- 在 Windows 上从干净目录按 README 命令可复现；不要求用户先安装 Go。

## 6. 顺序、工期与决策点

| 阶段 | 产物 | 单人估算 | 继续条件 |
|---|---|---:|---|
| 0. 竞品实测与用户访谈 | 对照表、3 份具体故障记录 | 1–2 天 | 有实际未解决问题，至少 2 人愿意试用 |
| 1. 双客户端技术刺探 | fixture、2 份真实客户端原始轨迹 | 2–4 天 | 两端都能隔离加载并可靠采证 |
| 2. 最小 CLI | manifest、适配器、确定性断言 | 5–8 天 | 四类场景稳定归因 |
| 3. 发行证据包 | HTML/JSON 报告、脱敏、版本对比 | 4–6 天 | 第三方可复现故障与修复 |
| 4. 试用修正 | 一个真实插件的升级前后验收 | 3–5 天 | 试用者认为报告比现有工具节省诊断时间 |

总计约 **3–5 周单人工作量**，是以两个立项门槛通过为前提的粗估；不包括 OAuth、ChatGPT UI 和跨操作系统支持。门槛失败就缩小或停止，不因已经写了基础设施而继续扩建。

## 7. 风险和应对

1. **竞品覆盖面大。** MCPJam 已做到真实 harness 评测，mcp-interop 已做到真实客户端发现。先做同题实测和用户访谈；不得把“支持两个客户端”当作卖点。
2. **认证与版本漂移。** 当前 Codex home 解析失败，Claude 安装版早于部分最新文档功能。用本机实际版本做兼容基线，事件解析保留未知字段；认证问题单独列为阻碍，不写成产品缺陷。
3. **模型不确定性。** 用服务端事件和确定性断言评测，保留全部迭代与失败；跨模型结果不混成一个分数。
4. **插件副作用与数据泄露。** 原型仅用虚构 fixture；真实插件测试先要求只读账号、最小权限和测试数据。报告默认本地保存、脱敏，不上传任务对话和令牌。
5. **协议代际差异。** 记录实际协商版本，先用两客户端都能运行的 stdio 路径；2026 协议新能力另列兼容矩阵，不由 SDK 宣称支持推断客户端支持。

## 8. 当前建议的下一步

先执行阶段 0 和阶段 1，并把结果作为是否正式建立新仓库的依据。此时最有价值的成果不是 UI，而是**一份真实双客户端调用轨迹 + 一张与 MCPJam 同题实测的差异表**。只有两者都支持差异化，才按第 5 节进入 MVP 开发。

## 9. 实施记录（2026-09-27）

用户随后要求按本方案编码。已建立 `ai-plugin-doctor/` 原型，具体命令和证据见 [实施状态](../IMPLEMENTATION_STATUS.md)。官方 SDK 直连、透明代理采证、Codex 与 Claude 的真实客户端工具发现和真实调用已经验证。早期两端五类任务各三次共 30 次 E2／E3 PASS；后续固定 Codex 模型、增加 E0 manifest、E1 受控调用和 `run_id` 断言后的最终批次，Claude 15/15、Codex 14/15 E0–E3 PASS。Codex 一次间接任务改用账号连接的 Drive/Gmail 搜索，虽发现目标服务却未调用，失败证据保留；当前隔离参数未排除账号连接器影响。已实测官方 Memory 服务升级前后和两端 schema 变更回归。MCPJam 本地同 fixture 握手/调用/兼容探针及 Cloud 托管真实模型五类任务各三次均完成；Cloud 12/15 trial 通过，三次失败均为预期工具错误被评为响应阶段失败，详见 [竞品对照](../research/comparison/COMPETITOR_COMPARISON.md)。三位目标用户访谈及至少两位试用者反馈仍待取得。竞品同题部分已完成，但门槛 A 的真实用户需求部分和完整产品价值验证尚未通过，计划不能称为全量完成。

## 10. 范围调整及最终技术验收（2026-09-28）

用户明确取消“三位真实用户访谈”和“至少两位试用者反馈”两项本次交付要求。第 4、6、9 节记录制定计划时的门槛和早期实施状态，以上变更以本节为准。没有访谈或试用数据，因此不宣称产品差异或节省诊断时间已获用户验证。

- Codex 增加账号应用连接器等能力的显式隔离参数后，五类任务各三次 E0–E3 **15/15 PASS**；Claude 同批 **15/15 PASS**。修复前 Codex 14/15 的失败报告仍保留。最终报告见 `ai-plugin-doctor/runs/final-codex-isolated-gate/report.json` 和 `ai-plugin-doctor/runs/final-claude-gate/report.json`。
- 官方 Memory MCP 服务包从 `2026.7.4` 升至 `2026.8.31`。固定两端各自的客户端、模型和隔离条件后，四个只读任务在升级前后均通过；工具表面哈希相同。记录见 [升级试验](../research/memory-upgrade/UPGRADE_TRIAL.md)。
- fixture 的工具参数 schema 从 `releaseId` 改为 `releaseCode`，两端的升级比较均识别 PASS→FAIL 并返回退出码 2。服务启动失败单独归类为 E1 FAIL，后续层级 SKIP。原始证据见 `ai-plugin-doctor/research/regression/` 和 `ai-plugin-doctor/runs/startup-failure-final-contract/`。
- Windows 干净目录完成 `npm ci`、构建、16 项测试、`init`、`preflight`，并分别在真实 Codex 与 Claude 执行一条任务，E0–E3 均通过。统一事件文件、客户端/服务版本、模型标识、哈希及费用字段已验证；Codex 未提供费用时标为未知。证据见 `ai-plugin-doctor/research/clean-install-evidence/`。

由此，调整后的首版**技术交付和自动化验收清单已完成**，详情见 [实施状态](../IMPLEMENTATION_STATUS.md)。E4 完整插件体验仍按首版设计为人工检查项，未经人工签署时显示 SKIP；HTTP/OAuth、MCP Apps UI、Skills 自动验收和其他客户端自动化依第 3 节属于延后范围。本轮结果只适用于记录的本机环境、版本、模型和任务，不外推为通用兼容率。
