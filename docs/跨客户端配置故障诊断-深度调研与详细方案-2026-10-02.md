# 跨客户端配置故障诊断：深度调研与详细方案

调研日期：2026-10-02。项目：AI Plugin Doctor。状态：供讨论的实施方案；产品功能尚未编码。本轮增加的是隔离调研脚本及证据。

## 1. 建议与产品目标

建议在现有项目上增加面向 AI 工具重度用户的“跨客户端配置诊断”工作流。用户指定当前工作区和出现差异的两个客户端，获得配置来源、实际覆盖关系、可验证的故障原因、最小修复建议及修复后的复查结果。

首版核心体验：同一个 MCP 服务在 Claude Code 能用、Codex 不能用时，用户能看见差异来自哪一份配置、哪个字段、哪条客户端规则，以及怎样确认修改生效。

目标用户通常同时使用两个以上 AI 客户端，有多个工作区、全局和项目配置、第三方模型端点及本机代理。第一版围绕 MCP 配置；模型端点和代理作为关联诊断上下文。Skills、Hooks、完整插件安装和模型供应商切换另行评估。

技术判断：配置发现、解析、作用域解释和差异诊断可行；本机 Codex/Claude CLI 的部分规则已经实测。完整桌面会话状态、OAuth 凭据、远程环境和扩展动态注册服务无法仅靠读本地文件确认，必须明确证据缺口。产品价值和用户付费意愿尚未验证；用户此前已免除访谈和试用反馈要求，本方案不重新设置这些前置条件。

## 2. 调研方法与可信度

本轮核对了四类客户端的官方文档、原项目代码、相关项目维护者的 README 和产品仓库中的故障报告，并在隔离目录中执行了合成配置实验。

证据标签统一为：

| 标签 | 含义 | 可以支持什么结论 |
| --- | --- | --- |
| 本机实测 | 指定版本客户端执行的结果 | 该版本、入口和测试条件下的具体行为 |
| 官方规则 | 官方文档明确的规则 | 按文档适用版本解释配置；不保证所有安装版本一致 |
| 用户报告 | 产品仓库 Issue 或官方社区中的报告 | 问题线索及回归样例；不能认定当前版本仍存在 |
| 方案设计 | 本项目拟实现的机制 | 可讨论的工程选择；不是已经交付的能力 |
| 待验证 | 缺少原生状态、实际版本或外部环境 | 保持未知，记录下一项验证动作 |

不会把“服务握手成功”“客户端加载成功”“模型实际使用工具成功”合并成一个健康绿灯。

## 3. 最新配置规则带来的实际问题

### 3.1 Codex：配置分层和信任共同决定是否加载

Codex 使用 TOML；配置有命令行、项目、Profile、用户等层级。项目层只在受信任项目中加载，距离当前目录最近的项目配置优先。MCP 服务还可通过启用开关和工具名单筛选；环境转发采用专门的 `env_vars` 等字段。[配置基础](https://learn.chatgpt.com/docs/config-file/config-basic) · [MCP 配置](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) · [配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

对产品的要求：记录工作目录、配置根目录和启动覆盖项；解释字段来源与被覆盖项。未知 Profile、信任状态或托管约束时不能宣称解析结果就是正在运行的会话状态。终端命令的 `shell_environment_policy` 与 MCP 的环境转发规则分别建模，不能套用同一套规则。

### 3.2 Claude Code：MCP 服务作用域与普通设置作用域不同

Claude 的 MCP 服务有 local、project、user 作用域。local 和 user 都可存于用户配置，但 local 按项目路径索引；同名服务采用最高优先级的整条定义。普通设置和权限来自另一套文件及合并规则。[Claude MCP](https://code.claude.com/docs/en/mcp) · [设置分层](https://code.claude.com/docs/en/settings)

对产品的要求：MCP local 与 `.claude/settings.local.json` 不混为一谈；服务定义采用整条选择，权限名单依照对应版本的独立合并规则解释。界面同时展示服务配置来源和权限来源。

### 3.3 环境变量表达式不能直接跨客户端复制

Claude 项目 MCP 使用 `${VAR}`；Cursor 使用 `${env:VAR}` 并提供工作区变量；VS Code 还支持 `${input:...}`。Codex 为变量转发提供专用字段。[Claude MCP](https://code.claude.com/docs/en/mcp) · [Cursor MCP](https://prod.cursor.com/docs/mcp) · [VS Code MCP 配置](https://code.visualstudio.com/docs/agents/reference/mcp-configuration) · [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

对产品的要求：保留表达式类型和来源；只依据目标客户端规则解析。VS Code 保存的交互输入不可通过读取配置取得实际值，应展示“由客户端保存，诊断器未读取”。不同配置中变量名不同不等于凭据一定不同。

### 3.4 同一个应用名称并不足以识别运行环境

Claude Desktop 的聊天 MCP 配置与 Claude Code 配置分别管理。VS Code 的本地聊天、远程窗口、Profile 及 Agent Host 也有不同配置来源；远程窗口的变量和文件可能在远端。[Claude Desktop](https://code.claude.com/docs/en/desktop) · [VS Code MCP 配置](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)

对产品的要求：一个诊断上下文至少含客户端、入口、版本、工作区、运行位置及 Profile。第一版中的 VS Code 明确指本地 Copilot Chat；Agent Host、Copilot CLI、WSL、SSH 和 Dev Container 标为另一个上下文，不能默认映射到本地用户配置。

### 3.5 网络、模型认证与 MCP 认证分别判断

Claude 支持标准 HTTP 代理环境变量；不同入口对变量来源有额外限制。网络变量、证书设置及本地绕过规则需要按客户端解释。[Claude 网络配置](https://code.claude.com/docs/en/network-config)

对产品的要求：先识别请求目标属于模型服务、MCP 服务还是代理。模型 401 不等于 MCP 服务认证失败；MCP 握手正常而模型不支持工具调用也不应归为配置错误。第三方模型接入是合法的独立配置场景，不要求改用官方 API key。

首版完成声明：四类配置读取、双 CLI 的规则和受限复查。不会写成“四客户端完整自动验收”。当前 Claude 版本已足够开展配置诊断，无需把协议 v2 升级设为前置条件。

### 6.2 主要交互

1. 选择当前工作区及出现问题的客户端入口。
2. 扫描配置和依赖；用户无需先写 `doctor.yaml`。
3. 展示按服务排列的差异，优先解释影响使用的字段。
4. 选择一个服务查看配置来源和诊断证据。
5. 如需连接检查，明确启动该服务；模型测试另选并显示费用未知或预算。
6. 查看修复前后字段及影响范围，应用受支持的修改或使用人工片段。
7. 重新扫描；分别显示配置更新、服务连接和原生会话验证状态。

首版采用本地 HTML 报告加 CLI：扫描结果打开即可查看，不要求部署网站或注册账号。HTML 采用静态内容与严格转义；不提供网页任意执行命令按钮。后续交互应用须另做本地桥接及访问控制。

预期报告示例（以下是示意数据）：

```text
服务：team-search
Claude Code：配置可用，项目定义生效
Codex CLI：配置被跳过，项目尚未信任

原因：Codex 当前项目层未加载；用户层没有对应服务。
证据：项目文件的位置 + 版本规则 + CLI 配置列表中未出现服务。
下一步：在 Codex 中审阅并信任项目，再重新核对。
状态：配置原因已确认；当前桌面会话尚未验证。
```

如果只取得文件和文档，没有 CLI/原生状态，示例中的“已确认”必须降级为“按规则推断”。

## 7. 数据模型与配置解释

### 7.1 上下文

`ClientContext` 记录 client、surface、version、executable、workspace、cwd、profile、configRoot、executionLocation、已知启动覆盖和证据时间。缺省项保持 unknown，不能猜成 default。

配置来源使用 `ConfigSource`：真实路径、本地显示别名、作用域、文件格式、读取结果、相关节点位置、是否可编辑、内容版本及适用客户端版本规则。缺失、不可读、损坏三个状态分别保留。

### 7.2 服务定义及来源

`ServerDefinition` 保留 command/args/cwd/url/transport/env/headers、凭据引用、启用/工具筛选、未知原生字段及其来源。内部表达式类型包括 literal、env-reference、input-reference、workspace-reference、helper、opaque。

原生语义优先：Codex 根据验证过的字段合并策略解释，Claude MCP 进行整条选择，权限与禁用规则独立解释。禁止将所有格式统一成一个丢失来源的 `mcpServers` 对象。

每个有效字段保留来源链，显示“来自用户层”“被项目层覆盖”“未加载：不受信任”等。未知字段保留；仅在已确认客户端不支持时给出版本相关提示。

### 7.3 同一服务的匹配

名称只是候选信号，不能唯一确定身份。优先使用用户确认的映射；其次比较传输方式、已解析执行入口/包标识、参数和端点等。HTTP 的路径、查询串、非默认端口可能有语义，不能随意移除。命令包装、Docker、不同账号或不同数据库的差异可能是有意的。

界面先展示“候选为同一服务”，歧义时由用户确认一次映射，存到项目自己的配置。只有明确匹配的服务进入修复计划。Windows 路径保留原文与规范表示；不全局转小写或把所有 symlink 当等价。

## 8. 故障规则与诊断结论

首版采用确定性规则，暂不依赖 LLM 判定故障。每条规则包含证据前提、适用版本、可能影响、修复动作、复查方法及反例。模型行为问题不由静态配置判定。

| 规则组 | 检查内容 | 结论约束 |
| --- | --- | --- |
| 文件与格式 | 缺失、不可读、语法错误、重复键、错误根键、必要字段 | 指到文件及节点；不读取整个用户目录 |
| 作用域 | 同名覆盖、未信任项目、未知 Profile、未知启动参数、managed 限制 | 说明实际覆盖或证据缺口；差异本身不是故障 |
| 启动 | 命令不存在、多个安装入口、工作目录缺失、相对路径基准、Windows 脚本类型 | 诊断器 PATH 证据仅描述诊断器；客户端环境需补证据 |
| 表达式 | 不兼容变量语法、变量未设置、交互输入不可访问、envFile 缺失 | 按客户端与入口处理，不显示实际值 |
| 传输 | command/url 冲突、目标不支持、缺少已知 type | URL 后缀不足以确定 HTTP/SSE；必要时让用户选择 |
| 工具权限 | 服务 disabled、工具 allow/deny、项目审批、权限合并 | 已发现工具不等于已获调用许可；不自动放宽权限 |
| 网络与认证 | 代理配置来源、端口连接、NO_PROXY 候选、证书路径、模型/MCP 401 | 不以终端 curl 成功推断所有客户端网络正常 |
| 缓存/版本/状态 | 旧会话、工具缓存、版本不在已验证范围、动态注册 | 只有明确证据才确诊；提供官方复查步骤 |

建议的首批规则 ID：`CFG_PARSE_ERROR`、`CFG_ROOT_KEY`、`CFG_REQUIRED_FIELD`、`CFG_DUPLICATE_KEY`、`CFG_SHADOWED`、`PROJECT_TRUST_REQUIRED`、`PROFILE_UNOBSERVED`、`MANAGED_POLICY_UNOBSERVED`、`COMMAND_NOT_FOUND`、`MULTIPLE_INSTALLATIONS`、`CWD_MISSING`、`RELATIVE_PATH_CONTEXT`、`WINDOWS_LAUNCHER_MISMATCH`、`VAR_DIALECT_MISMATCH`、`VAR_MISSING`、`INPUT_VALUE_UNOBSERVED`、`ENVFILE_MISSING`、`TRANSPORT_AMBIGUOUS`、`SERVER_DISABLED`、`TOOL_FILTERED`、`PROJECT_APPROVAL_REQUIRED`、`PROXY_CONTEXT_DIFFERENCE`、`AUTH_TARGET_UNCLASSIFIED`、`CLIENT_STATE_UNOBSERVED`。

诊断输出使用四种类别：已确认、按规则推断、可能原因、尚未验证；严重性和置信度分别表达。比如“Token 不同”不是已确认故障，因为账号差异可能有意；“新旧工具列表不同”也可能是权限或缓存，而非配置错误。

多重故障按依赖排序：先处理语法/文件读取，再解释覆盖和表达式，再做启动/连接，最后检查工具与任务。修复第一项后继续检查其余项，不能以一个原因掩盖全部问题。

## 9. 四类证据及验证边界

| 证据 | 获取方式 | 不应推导出的结果 |
| --- | --- | --- |
| 文件证据 | 读取相关字段，按版本规则解释 | 当前进程一定已加载 |
| CLI 配置证据 | 经过验证的无服务器启动读取命令；输出先脱敏 | 工具可见、权限通过或模型可用 |
| 受控服务证据 | 用户选中服务后，使用指定环境启动并发现工具 | 原生 IDE/桌面环境一定相同 |
| 原生会话证据 | 目标入口状态/日志、明确授权的原生验证 | 所有入口、版本和账号均正常 |

现有隔离运行器的证据注明 `controlled-replay`；不把它用于给原生会话盖通过章。Codex 当前 `mcp list --json` 用于配置核对；原始输出可能含敏感字段，禁止直接终端回显或保存。

Claude Code 2.1.89 本机帮助明确表示 `mcp get/list` 会启动服务并跳过工作区信任对话。因此被动扫描不运行这两个命令；主动阶段只检查已选服务，用户先看到会启动什么。启动服务本身就可能产生副作用，即使不调用任何工具。

受控连接默认只进行发现；业务工具调用另需明确指定无副作用测试和参数。客户端任务验证可能产生模型费用，应展示固定模型及预算/未知费用，复用原项目的单次预算能力。

Cursor 官方 CLI 文档提供 `agent mcp list-tools`，但本机未找到 CLI，暂不承诺自动化解析和行为等价。VS Code 官方扩展 API 能注册 MCP 服务，调研页未建立一个通用接口可读取全部服务的信任、凭据及实时状态，故首版采用明确的人工取证步骤。[Cursor CLI](https://prod.cursor.com/docs/cli/mcp) · [VS Code 扩展 API](https://code.visualstudio.com/api/extension-guides/ai/mcp)

## 10. 修复计划与恢复

首版以字段级修复预览为核心。`RepairPlan` 包含目标文件/作用域、语义修改、预期前置条件、影响范围、不可修改项和复查动作；凭据保持引用，计划不保存原始秘密。

可支持的受限修改：已验证格式中的变量表达式转换；由用户确认的执行文件或 cwd；已确认客户端格式下的必要字段修正。跨客户端导出仅覆盖明确可映射的字段，其余逐项提示。

这些情形采用人工动作：项目信任、工具允许/拒绝、账号权限、OAuth 登录、托管策略、动态注册服务、未知启动器以及无稳定编辑器的 TOML 结构。不会以通用“全部放行”“全部重置”作为修复。

应用流程：

1. 将选择的修改渲染到内存，重新解析并验证。
2. 检查目标文件类型、路径、原始内容版本及当前作用域；文件有变化时拒绝旧计划。
3. 对每个目标文件串行修改，保留带访问限制的原文件备份；JSON/JSONC 保持注释、换行及无关字段。
4. 通过同目录临时文件完成单文件替换，记录写入结果；不宣称跨客户端文件事务绝对原子。
5. 复查配置及可执行的验证步骤；连接失败不等于文件修改没有完成，两种状态分别展示。
6. 后续文件操作失败时尝试恢复已写入文件；恢复前再次检查是否被其他程序修改，冲突时停止并报告。

备份可能含原有秘密，默认留在用户本机，不纳入 Git 或分享包；清楚列出路径和恢复命令。OneDrive 等同步目录或其他配置管理器同时修改文件时，必须基于版本检查拒绝覆盖，并建议暂停冲突操作。

实施期间真实用户配置的改动须由用户选择并触发。开发验证只在合成目录完成。此处是产品交互要求，不是当前调研需要额外确认的理由。

## 11. 隐私与执行控制

配置读取仅遍历客户端已知路径和明确工作区，限制文件大小、层级和数量；不递归搜索磁盘。处理符号链接、junction 和非普通文件时显示目标，自动修改只支持已验证的普通文件。

配置语义会接触秘密，应在内存中提取允许展示的字段。所有 env/header/URL 查询值及未知参数默认按敏感内容处理；只保留变量名、是否存在及等价/不同状态。明文 args 不能因为键名叫 args 就直接输出。

同一次扫描内可用随机密钥 HMAC 比较已知凭据是否相等；密钥留内存，报告只输出关系，不输出摘要。无法取得客户端 input/keychain/OAuth 值时标记 unknown。跨次扫描不通过凭据摘要宣称相等或变化。

报告默认不保存原始配置、全部环境变量、认证文件或业务工具参数。原生日志先按目标服务和时间范围截取、脱敏；不默认导入全部聊天记录。HTML 转义全部外部文本，分享包再次验证脱敏。

扫描默认不启动服务、不执行 headersHelper/apiKeyHelper、不运行 npx 下载、不读取 OAuth 令牌。主动测试显示选择项；运行固定 argv，不把配置字符串拼成 shell 命令。Windows 批处理包装必须采用已验证的调用方式，对无法安全表示的命令拒绝自动执行。

为 connect/list/call/进程退出分别设置时限，限制并发及输出大小。Windows 进程树控制先做可行性验证；若无法可靠收尾，主动功能不能通过发布门槛。解析器自身故障时给出错误，不能显示“没有发现问题”。

## 12. 架构与依赖选择

建议的新模块：

```text
src/diagnostics/
  context.ts           当前工作区、入口、版本和运行位置
  discovery.ts         只读路径及安装候选发现
  adapters/            codex / claude / cursor / vscode
  parsers/             JSON / JSONC / TOML
  provenance.ts        覆盖关系及字段来源
  identity.ts          服务候选匹配与用户映射
  rules/               版本相关故障规则
  evidence.ts          文件、CLI、服务及原生会话证据
  repair-plan.ts       字段级计划与前置条件
  repair-apply.ts      受限修改、备份和恢复
  report.ts            面向用户的故障报告
```

JSONC 候选依赖采用 Microsoft `jsonc-parser`：其节点偏移和 modify/applyEdits API 可用于局部修改；必须检查错误列表及重复键，不能把容错解析成功当成格式有效。[项目说明](https://github.com/microsoft/node-jsonc-parser)

TOML 候选阅读器采用 `smol-toml`，正式添加依赖前固定版本并核对 Codex 所接受的 TOML 子集。[项目说明](https://github.com/squirrelchat/smol-toml) 解析/序列化不代表能保留源文件注释，第一版复杂 TOML 修改导出人工片段；只有字段范围定位、无关内容保持和重新解析均通过专项验证，才开放自动修改。不得整文件 stringify 覆盖用户配置。

读取诊断与 MCP SDK 协议实现解耦；无需为这项工作先升级 SDK v2。主动探测只在当前 SDK 能支持的协议和传输下执行，其他场景报告不支持。远程 HTTP/OAuth 完整诊断属于后续里程碑。

建议新命令（拟议接口，尚未实现）：

```text
doctor scan --workspace <path> --clients codex,claude,cursor,vscode --out <directory>
doctor diagnose <scan.json> --service <id>
doctor check <scan.json> --client claude --service <id>
doctor plan <scan.json> --finding <id> --out <plan.json>
doctor apply <plan.json>
doctor verify <plan.json>
doctor restore <operation-id>
```

`scan` 不需要 DoctorConfig；现有 preflight/run 仍接收旧配置。修复前后报告有独立 schemaVersion，与 E0–E4 发行验收报告分开；CLI/HTML 共享同一诊断数据。

## 14. 验收设计

### 14.1 合成故障集

设置 24 项首版场景，每项都有正确配置对照和期望证据级别：

1. JSON 语法错误；2. JSONC 注释/尾逗号；3. TOML 读取；4. 重复键；5. 根键错配；6. 必要字段缺失。
7. Claude local 覆盖；8. project 覆盖；9. Codex 项目未信任；10. 命令行覆盖；11. 未知 Profile；12. managed 来源不可读。
13. 变量语法错配；14. 变量缺失；15. input 值不可观测；16. envFile 缺失；17. 命令不存在；18. cwd/相对路径基准差异。
19. 多安装入口；20. Windows 启动包装；21. 服务 disabled；22. 工具筛选/权限；23. 远程或不同入口；24. 多重故障排序。

其中 8 项对应本轮本机实验的子条件；其余尚待实现和验证。不同客户端不支持的功能作为 unknown/unsupported 对照，不计为自动诊断成功。

### 14.2 发布要求

- 固定版本与支持矩阵内的 24 个场景达到各自期望结果；额外设置至少 12 个有意不同/健康配置对照，不能误判为必须修复。
- 被动扫描不执行 fixture 启动器、凭据 helper 或模型请求；通过哨兵文件确认。
- 报告、终端输出及分享包中的合成秘密 canary 泄漏数量为 0；测试包含自由文本、URL 路径/查询、args、异常和原生输出。
- 至少 4 类受限修改完成预览、应用及静态复查；目标客户端和格式以实测支持矩阵为准。
- 至少 2 个双 CLI 故障样例补齐目标入口证据或明确人工步骤；受控回放不能替代缺失的原生证据。
- 修复测试覆盖并发修改、第二文件写入失败、恢复冲突、注释/无关字段保持；不能以局部成功报告全量成功。
- 连接超时、服务崩溃、巨大输出和中断后，本工具启动的进程得到有界收尾。
- 旧项目 build/test 门槛仍通过；新增诊断工作不会要求用户先配置发行测试任务。

这些是拟议验收标准，不是本轮已完成结果。精度和用户节省时间的百分比需要后续数据，当前不编造。

## 15. 风险与决策

| 风险 | 对策或边界 |
| --- | --- |
| 官方文档快于用户安装版本 | 记录版本，优先已实测规则；不支持范围内的规则保留未知 |
| 客户端没有稳定状态读取接口 | 明确人工取证；不读取私有数据库伪装成长期稳定接口 |
| 诊断器环境与 IDE 环境不同 | 记录采集位置；必要时在目标入口启动无秘密探针，另行验证接入方式 |
| 同名服务身份不一致 | 用户映射和来源解释；差异不自动同步 |
| 配置管理器或云盘同时写入 | 陈旧检查、逐文件记录、冲突停止；不操作竞争工具数据库 |
| 秘密通过 args/URL/日志泄露 | 默认隐藏值、字段允许展示、合成 canary 验收 |
| 模型故障被误当配置故障 | 按目标分层，并保留第三方模型配置；task 行为诊断另列 |
| MCP 协议升级扩大范围 | 扫描与协议 SDK 解耦；先完成配置故障闭环 |

建议讨论并确定的实施边界：Windows 优先，Codex CLI/Claude Code 为实测核心，Cursor IDE/VS Code 本地 Chat 做配置诊断；默认只读扫描；修复限定到能够验证的字段和作用域；复杂 TOML、权限、认证及远程会话保留人工动作。按此范围可以逐步交付，并对未验证的部分保持准确声明。

后续开始编码时，先落实 P0 的剩余执行控制验证和 P1 读取适配器。业务重点是配置来源、变量和作用域诊断，协议 v2 迁移暂不设为前置工作。
